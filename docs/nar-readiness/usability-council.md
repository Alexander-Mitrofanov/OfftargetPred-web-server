# Usability council: OfftargetPred for a NAR Web Server proposal

**Review date:** 19 September 2026. **Scope:** recommendations only; no application, model, deployment, or production changes. Sequence-only SpCas9 candidate assessment; no CasKAS or epigenetic features.

## Decision

The current application is a credible functional starting point. Prioritize interpretation, reproducibility, recovery, and beginner access before adding more predictors. A useful next release would let a researcher resolve a guide, inspect biologically contextualized candidates, compare the three existing models transparently, and export an auditable shortlist.

The council's central memo owns the eligibility and timing assessment against the [official NAR guidance](https://academic.oup.com/nar/pages/Submission_Webserver).

All proposed features and acceptance targets below are this reviewer's recommendations, not claims that they already exist or that passing them guarantees publication.

## Evidence and confidence

### Verified in source and supplied acceptance evidence

- **Existing input paths:** one guide with candidate sequences; CSV/TSV paste or upload; accepted column aliases; row-specific validation; FASTA/plain-text genome guides. Inputs require 23 bases including actual PAM. Genome search supports installed GRCh38 primary assembly, NGG, both strands, 0–4 protospacer substitutions, and at most ten guides. See [input.ts](../../frontend/src/input.ts), [App.tsx](../../frontend/src/App.tsx), and [model card](../model-card.md).
- **Existing result features:** per-model scores, mismatch/PAM highlighting, global text filter, sorting, pagination, exact-protospacer label, CSV and JSON downloads, cancellation, deletion, private result links, and 24-hour retention. JSON includes model/reference provenance; results API also returns metadata, but the frontend `Results` type does not expose it. See [frontend API](../../frontend/src/api.ts), [HTTP API](../API.md), [worker](../../backend/offtargetpred/worker.py), and `ResultsPanel` in [App.tsx](../../frontend/src/App.tsx).
- **Existing explanation:** separate help/about pages explain orientation, PAMs, unknown bases, model disagreement, search limits, and uncalibrated scores. Do not recommend these as missing. No login or email is needed.
- **Existing accessibility groundwork:** skip link, labels, visible focus styles, reduced-motion CSS, keyboard-focusable table scroller, live regions, and mismatch underline in addition to color. This is useful groundwork, not a completed accessibility audit. See [styles.css](../../frontend/src/styles.css) and [App.tsx](../../frontend/src/App.tsx).
- **Existing launch evidence:** [public browser report](../validation/public-browser.json) records real pair scoring, GRCh38 search, GPU output/downloads, refresh, deletion, no JS errors, and no page overflow at 390px. [Browser script](../../tests/browser/live_flow.py) launches Playwright Chromium using Google Chrome. This does not establish Firefox or Safari compatibility.
- **Visual evidence inspected:** existing desktop and mobile screenshots in `output/playwright/live-results-desktop.png` and `live-results-mobile.png`. Desktop example scores cluster near 0.994–0.996; this example verifies the flow but shows little score diversity. Mobile results require horizontal scrolling to reach score columns. These are visual observations, not measured user difficulties.
- **Missing in the inspected frontend:** interactive precomputed result route, standard licence on landing page, dedicated contact/citation links, gene/locus entry, 20-nt guide resolution, genome-browser links, gene annotations, per-guide summary, and downloadable interpretation report. Static input examples already exist.
- **Unresolved provenance claim:** `App.tsx` around line 383 asserts seed-0 models. The model card records README seed 0 and checkpoint config seed 42 and avoids asserting a verified seed. A saved default seed does not establish the actual run seed, which could have been supplied separately. Obtain run provenance or use the model card's cautious wording; do not replace the claim with an assertion of seed 42.

The root council member separately inspected the live homepage and confirmed the input/footer observations. This reviewer inspected repository files and existing screenshots; the web-fetch tool could not retrieve the live frontend or health URL, which is not evidence of an outage. No new GPU jobs were submitted.

### Scientific display dependency

The scientific council has reported one shared guide and 981 exact pairs between supplied K562 evaluation data and the reported T-cell training corpus. Actual checkpoint training membership remains unverified. Its documented overlap audit must determine the exact exclusions and revised claims. This reviewer has not independently reproduced that audit. Until it is resolved, treat the existing K562 results as reproducibility evidence with an independence caveat; do not promote the entire file as clean held-out validation. The current [benchmark JSON](../validation/model-benchmark.json) reports five evaluated guides and reproduced metrics but does not itself demonstrate absence of training overlap.

## Intended user journeys

### Wet-lab beginner: “I have a guide and want candidate sites to check”

1. Choose **Find candidate sites**; see human GRCh38 primary assembly and NGG support immediately. Explain in ordinary language what a PAM is and which DNA strand/orientation the input represents.
2. Paste either the full 23-nt target sequence or a 20-nt guide. For 20 nt, resolve exact reference matches and present their actual PAMs and loci. The researcher confirms the intended locus; ambiguous matches remain explicit. Never append an invented PAM.
3. Review the resolved 23-nt sequence, locus, search scope, selected k=1 model, and retention. Model comparison is an optional expansion. Provide a persistent interactive example if the user wants to learn before running.
4. Receive a recoverable result link immediately. After completion, see candidate count, intended-locus handling, reference/search scope, and an explanation of score meaning.
5. Open a candidate's sequence alignment and genomic context, inspect high-scoring candidates, and export a shortlist plus full results/provenance. The researcher chooses experimental follow-up; the interface makes no safety verdict.

**Pilot target:** at least 5 of 6 beginners complete the example task without facilitator intervention; median hands-on time under five minutes, excluding computation; all can explain that a score of 0.9 is not a 90% editing probability after the tutorial.

### Advanced researcher: “I have several guides or a candidate table”

1. Upload a supported table; inspect detected column mappings, row counts, duplicate IDs, warnings, and retained metadata before submission. Or select up to ten guides from a bounded gene/locus workflow.
2. Choose one or all existing models and explicit reference/search settings. Save the normalized input and request parameters.
3. Group candidates by guide, compare per-model ranks and disagreement, apply clear filters, and inspect annotation provenance. Pair-only jobs are labelled as supplied candidate lists with unknown completeness.
4. Export full/filtered/selected records with explicit scope, BED for genomic rows, a machine-readable run manifest, and a concise methods/report file. Reproduce the example through an API client if desired.

**Pilot target:** at least 5 of 6 advanced users import a deliberately messy table, recover a private result, identify a discordant candidate, and export the requested subset plus manifest without assistance; all retain the correct assembly and coordinate convention.

## Integration sequence

1. **Readiness prerequisites:** U01–U04, U14, U17–U18. Align claims and rights, supply durable interactive output, secure recovery, and record usability evidence. Existing CSV/JSON and alignment components should be extended rather than rebuilt.
2. **Smallest coherent decision workflow:** 20-nt guide plus explicit locus/actual PAM (U05) → complete candidate search → pinned gene/exon context (U10) → separate model ranks (a small U08/U09 implementation) → user-selected experimental shortlist → labelled bundle and methods report (U12/U13). Prioritize one candidate detail view over several dashboards. Reference/PAM resolution precedes scoring; annotation never changes the sequence-only model.
3. **Follow-up improvements:** U07, richer U08/U09 visualization, U11, U15–U16. Gene-name/locus-based guide nomination (U06) follows only after bounded region handling and identifier/annotation provenance are reliable. Avoid promising every species or arbitrary nuclease to increase apparent breadth.

### Cross-review decision: the first two features to drop

After direct discussion with the integration and scientific members, drop **embedded IGV** first: coordinate-correct locus links and BED provide immediate genomic context with much less frontend and reference-track work. Drop **live CFD/MIT computation** second: retain these as independently audited offline evaluation comparators first. Neither is needed to complete the guide → candidate → shortlist workflow. Additional predictors and a genome viewer should not displace independent evidence, resolved PAM input, durable sample output, or provenance.

The shortlist should retain immutable candidate identity/row index, guide/locus, every selected model's value/rank, annotations with source, and optional researcher notes. State its selection count and export scope. Exclude an intended locus only after the researcher identifies it explicitly; never discard all perfect matches as on-target. Keep full candidate results available beside the selected set.

The science member proposes a testable biological-value study: recovery of assay-observed sites at fixed experimental shortlist budgets, compared with mismatch count and compatible baseline scoring on identical candidate universes. That study is separate from user satisfaction and task-completion evidence. Rank disagreement must be described as disagreement, not statistical uncertainty. Frozen examples should preserve full candidate counts and manifests, include a hard case, and label assay outcomes as observed or not detected with their experimental context; absence of detection is not universal biological inactivity.

Genome browsers and Ensembl-derived context are the first useful integrations: they help interpret this server's own candidate computations. Adding a menu of third-party scoring services would increase maintenance and privacy complexity without resolving the main present user tasks. A Galaxy wrapper or richer programmatic workflow is a later option after API versioning, async recovery, and a tested minimal client are stable; it should not become a prerequisite for use.

## Usability study and release decision

Recruit approximately six wet-lab researchers with little command-line experience and six experienced CRISPR analysts who did not develop the interface. Treat this as formative testing, not a statistically powered superiority claim. Give each group matched, non-sensitive tasks and preserve the same fixtures/build for before/after comparison. Record assisted completion separately from unassisted completion and report individual results as well as medians; do not hide failures in an average usability score.

Core tasks: select the appropriate mode; repair a 20/23-nt or orientation issue; interpret a mismatch/PAM alignment; explain score meaning; identify a candidate whose ranks differ between models; recover a job in a fresh browser; export the requested subset with correct provenance; identify what a zero-result search does not prove. Counterbalance task order where practical. Use existing frozen examples for most sessions so queue load and network variance do not dominate usability measurements; perform small real end-to-end runs separately.

Suggested release gate: at least 5/6 unassisted task completion in each group for its primary journey; no unresolved privacy/recovery or scientific-interpretation blocker; all participants correctly reject probability/safety interpretations after the explanation; every downloadable example opens and retains provenance; no severity-1/2 failures in the recorded browser matrix. These are internal targets, not NAR rules. Re-run the affected tasks after fixes and record what changed.

## Questions for other council members

- **Scientific validity:** What exact training/evaluation overlap remains after normalization and reverse-orientation checks? Which performance claims can the UI support after decontamination? Can two measured examples illustrate model disagreement without cherry-picking a performance claim?
- **Scientific validity:** Can the intended on-target locus be stored independently of scoring and shown without implying a unique sequence match? What annotation categories are scientifically supportable and reproducible across releases?
- **Infrastructure/API:** What recovery mechanism can safely handle submission timeouts and delayed worker starts? Can the API expose retry details and measured progress stages without a misleading ETA? Does every export preserve enough metadata and original row identity?
- **Rights and ownership:** Who authorizes the standard service/software licence and any model/sample-data redistribution? Which real contact, maintenance commitment, and citation can be published?
- **Integration scope:** Which gene annotation release can be frozen alongside the present Ensembl 115 primary assembly, and which reference names/coordinate transforms need integration tests for UCSC/Ensembl exports?
